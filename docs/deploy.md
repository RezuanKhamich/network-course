# Развёртывание на VPS (Рег.ру)

```
браузер ──HTTPS──▶ nginx ─┬─ /            статика из /srv/devcourses/web (сборка Vite)
                          └─ /api/  ──▶  Node.js 127.0.0.1:3000 (служба devcourses-api)
                                               │ unix-сокет
                                               ▼
                                         PostgreSQL (только локально)
```

Всё, что нужно на сервере, ставит и настраивает [`deploy/provision.sh`](../deploy/provision.sh). Дальше каждый push в `master` проходит тесты и выкладывается GitHub Actions ([`.github/workflows/ci.yml`](../.github/workflows/ci.yml)).

## Порядок

1. Перевести GitHub Pages на отдельную ветку со старым сайтом (раздел 9), чтобы слияние не сломало github.io.
2. Влить рабочие ветки в `master`. Пока переменная `DEPLOY_ENABLED` не задана, CI только прогоняет тесты.
3. Сервер, домен и `provision.sh` — разделы 1–3.
4. Секреты и переменные GitHub, первый деплой — разделы 4–5.
5. Почта, бэкапы, мониторинг — разделы 6–8 и чек-лист.

## Что понадобится

- **VPS на Рег.ру** (облачный сервер) с образом Ubuntu 24.04 или 26.04 LTS без предустановленных приложений. Хватит минимальной конфигурации: 1 vCPU, 1–2 ГБ памяти, 10+ ГБ диска. Подойдёт и любой другой провайдер с этими версиями Ubuntu — от Рег.ру тут ничего не зависит.
- **Домен** с доступом к DNS.
- **Почтовый ящик для писем сайта**, например `no-reply@ваш-домен`, с доступом по SMTP. Например, Яндекс 360 или Mail.ru для бизнеса с подключённым доменом.
- **SSH-ключ** на вашем компьютере (`ssh-keygen -t ed25519`, если ещё нет).

## 1. Сервер и домен

1. В панели Рег.ру создайте облачный сервер с образом Ubuntu LTS и при создании добавьте свой публичный SSH-ключ.
2. В управлении DNS-зоной домена создайте запись `A` для `@` с IP-адресом сервера. Запись для `www` — по желанию: если она есть, скрипт выпустит сертификат и на неё и будет перенаправлять `www` на основной адрес.
3. Дождитесь, пока записи начнут отвечать: `nslookup ваш-домен` должен вернуть IP сервера. Без этого не выпустится сертификат.

## 2. Ключ для деплоя

На своём компьютере создайте отдельный ключ, которым GitHub Actions будет заходить на сервер:

```bash
ssh-keygen -t ed25519 -f devcourses_deploy -N "" -C github-actions-deploy
```

`devcourses_deploy.pub` понадобится на шаге 3, `devcourses_deploy` (закрытый ключ) — на шаге 4. Больше нигде закрытый ключ не храните.

## 3. Настройка сервера

```bash
ssh root@IP-сервера
git clone https://github.com/RezuanKhamich/network-course.git /opt/devcourses-src
cd /opt/devcourses-src && git checkout master
DOMAIN=ваш-домен LE_EMAIL=ваша-почта DEPLOY_PUBKEY="содержимое devcourses_deploy.pub" bash deploy/provision.sh
```

Скрипт:
- ставит nginx, PostgreSQL, certbot и Node.js 22;
- создаёт пользователей `devcourses` (под ним работает API) и `deploy` (через него приходит выкладка; через sudo ему разрешён только перезапуск API);
- создаёт базу, к которой можно подключиться только локально через сокет, без пароля;
- открывает в межсетевом экране только SSH, HTTP и HTTPS;
- оставляет вход по SSH только по ключу;
- выпускает сертификат Let's Encrypt и включает ежедневный бэкап базы.

Повторный запуск безопасен.

Затем впишите пароль почтового ящика:

```bash
nano /etc/devcourses/api.env   # строка SMTP_URL
```

Сервер SMTP: у Яндекс 360 — `smtp.yandex.ru:465`, у Mail.ru для бизнеса — `smtp.mail.ru:465`. Логин — полный адрес ящика, пароль — пароль приложения, созданный в настройках безопасности ящика. Символ `@` в логине внутри `SMTP_URL` записывается как `%40`. Порт 25 провайдеры VPS часто блокируют, поэтому используется 465.

### Временно без домена

Пока домена нет, сайт можно поднять по IP-адресу:

```bash
PUBLIC_IP=IP-сервера bash deploy/provision.sh
```

В этом режиме нет HTTPS: трафик, включая пароли, идёт открытым текстом. Используйте его только для просмотра и тестовых аккаунтов. Cookie сессии выдаётся без флага `Secure`. Письма не отправляются, а пишутся в журнал: ссылку подтверждения регистрации можно взять из `journalctl -u devcourses-api`. Когда появится домен, запустите скрипт ещё раз с `DOMAIN` и `LE_EMAIL`. Он выпустит сертификат, переключит nginx на HTTPS и поправит `APP_ORIGIN`. Почту (`SMTP_URL`, `MAIL_FROM` вместо `MAIL_TRANSPORT=log`) в `/etc/devcourses/api.env` впишите вручную — скрипт напомнит об этом.

## 4. GitHub

**Settings → Environments → New environment → `production`.** Здесь можно включить Required reviewers, чтобы каждую выкладку подтверждали вручную.

**Settings → Secrets and variables → Actions:**

| Тип | Имя | Значение |
|---|---|---|
| Secret | `DEPLOY_SSH_KEY` | содержимое `devcourses_deploy` (закрытый ключ) |
| Secret | `DEPLOY_KNOWN_HOSTS` | вывод `ssh-keyscan -t ed25519 IP-сервера` |
| Variable | `DEPLOY_HOST` | IP-адрес сервера |
| Variable | `DEPLOY_DOMAIN` | ваш домен |
| Variable | `DEPLOY_ENABLED` | `true` |

Ключ сервера в `DEPLOY_KNOWN_HOSTS` защищает от подмены сервера, поэтому сверьте его с настоящим. На сервере выполните `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`, на своём компьютере — `ssh-keyscan -t ed25519 IP | ssh-keygen -lf -`. Отпечатки должны совпасть.

## 5. Первый деплой

Влейте рабочую ветку в `master` или запустите workflow вручную: **Actions → CI → Run workflow** на ветке `master`. Задача `deploy`:
1. загружает код сервера и ставит зависимости;
2. перезапускает API, при старте применяются миграции базы;
3. выкладывает статику целиком за один шаг;
4. проверяет `https://домен/api/health`.

После этого проверьте:
- открывается главная, работают курсы;
- регистрация: письмо пришло, а не попало в спам, ссылка открывает сайт и входит в аккаунт;
- [SSL Labs](https://www.ssllabs.com/ssltest/) показывает оценку A или выше;
- [securityheaders.com](https://securityheaders.com) видит CSP, HSTS и остальные заголовки.

## 6. Почта: SPF, DKIM, DMARC

Без этих записей письма с подтверждением будут уходить в спам. Почтовый сервис при подключении домена покажет нужные записи SPF и DKIM — добавьте их в DNS-зону домена. DMARC добавьте сами:

```
_dmarc  TXT  "v=DMARC1; p=quarantine; rua=mailto:ваша-почта"
```

Проверить настройку можно на [mail-tester.com](https://www.mail-tester.com): отправьте туда письмо через «Забыли пароль?».

## 7. Бэкапы

Дамп базы снимается каждый день в 03:30, локально хранится 14 дней в `/var/backups/devcourses`. Если сервер выйдет из строя, локальные копии пропадут вместе с ним, поэтому настройте копию во внешнее хранилище, например в S3-хранилище Рег.ру или Yandex Object Storage:

```bash
apt-get install -y rclone
rclone config --config /etc/devcourses/rclone.conf     # remote типа s3, данные из панели хранилища
chmod 600 /etc/devcourses/rclone.conf
echo 'BACKUP_RCLONE_REMOTE=s3:имя-бакета/devcourses' > /etc/devcourses/backup.env
systemctl start devcourses-backup && journalctl -u devcourses-backup -n 5
```

Срок хранения во внешнем хранилище задайте правилом жизненного цикла бакета.

**Бэкап, из которого ни разу не восстанавливались, — не бэкап.** Проверка восстановления:

```bash
f=$(ls -t /var/backups/devcourses/*.dump | head -1)
runuser -u postgres -- createdb restore_check
runuser -u postgres -- pg_restore -d restore_check "$f"
runuser -u postgres -- psql -d restore_check -c 'SELECT count(*) FROM users'
runuser -u postgres -- dropdb restore_check
```

## 8. Эксплуатация

| Задача | Команда |
|---|---|
| Логи API | `journalctl -u devcourses-api -f` |
| Статус и перезапуск | `systemctl status devcourses-api`, `systemctl restart devcourses-api` |
| Логи nginx | `/var/log/nginx/access.log`, `error.log` |
| Проверка продления сертификата | `certbot renew --dry-run` |
| Нужна ли перезагрузка после обновлений | `cat /var/run/reboot-required` |

- **Откат** — `git revert` проблемного коммита и push в `master`. Миграции базы только добавляют изменения. Если откатывается коммит с миграцией, нужна новая миграция, отменяющая изменения.
- **Мониторинг:** подключите внешнюю проверку доступности `https://домен/api/health` раз в несколько минут, например в UptimeRobot.
- **Обновления безопасности ОС** ставятся автоматически (`unattended-upgrades`).

## 9. Переезд пользователей с GitHub Pages

Прогресс гостей лежит в `localStorage` браузера и привязан к адресу `rezuankhamich.github.io`, поэтому на новый домен сам не переедет. Перед тем как вливать изменения в `master`:

1. Старый сайт переносится в отдельную ветку, и в настройках Pages выбирается она: **Settings → Pages → Branch**. После этого изменения в `master` больше не ломают github.io.
2. На старом сайте появляется баннер «Сайт переехал» с кнопкой переноса прогресса на новый домен. Пока кнопки нет, работает старый путь: «Данные → Скачать копию» на старом сайте, затем «Данные → Загрузить из файла» на новом.

## Чек-лист перед запуском

- [ ] Реквизиты оператора в политике обработки персональных данных (`#/privacy`) заполнены.
- [ ] Отправлено уведомление об обработке персональных данных в Роскомнадзор (портал персональных данных РКН).
- [ ] SPF, DKIM и DMARC настроены, письма не попадают в спам.
- [ ] Внешняя копия бэкапов настроена, восстановление проверено.
- [ ] Мониторинг `/api/health` включён.
- [ ] Шрифты Google Fonts по желанию перенесены на свой сервер: сейчас браузеры пользователей обращаются к серверам Google за рубежом.
